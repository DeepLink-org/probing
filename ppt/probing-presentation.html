01 价值和意义
如果用云原生语言理解 Probing
Probing 之于 AI 训练诊断 ≈ K8s 之于容器编排 — 从碎片化工具到统一平台
K8s / 云原生  →  Probing
Kubelet in every Node → Probe in every Rank
kubectl (声明式 YAML) → SQL (声明式查询)
CRD / Operator → Skills (steps.yaml)
CSI / CNI 标准接口 → ProbeDataSource 契约
KubeFed / Cluster API → global.* 联邦查询
Prometheus pull-based → 没有北向流量
Sidecar 注入 (webhook) → PROBING=1 / inject
OperatorHub / Helm Hub → Skills 社区市场
同一个级别的意义
K8s 统一了碎片化的容器编排生态：Mesos / Swarm / Nomad → 统一 API + 声明式模型。

Probing 正在统一碎片化的训练诊断生态：Nsight / PyTorch Profiler / Megatron profiler → 统一 SQL + Agent 接口。

两者都是从"每个团队写脚本"到"声明一个意图"的范式跃迁。
但难度更高
K8s 管理的是无状态容器——Pod 挂了可以重启，调度失败可以重试。

Probing 管理的是有状态训练进程——不能重启、不能中断、不能有可感知开销。万卡训练一次中断损失数十万元，zero-overhead 不是优化目标而是生存约束。

相当于在不能停机的生产数据库内部建一套 K8s 控制面。
一句话给老板：K8s 让部署从写脚本变成写 YAML；Probing 让诊断从写脚本变成写 SQL。K8s 管无状态容器可重启，Probing 管有状态训练进程不能中断——这是更硬的约束，也是更深的护城河。

02 技术方案和独特性
创新设计 (一)：没有北向流量 — 范式的根本选择
不是实现细节，而是架构哲学：数据不动，查询动

传统方案：北向汇聚

rank 0 → collector → 中心服务器
rank 1 → collector → 中心服务器
rank N → collector → 中心服务器
四大问题：
• 带宽 O(N) 放大，中心节点网络瓶颈
• 中心节点单点故障 = 诊断全断
• 序列化+网络IO 侵入训练热路径
• 中心节点需存储全量数据
VS

Probing：数据留存在本地

rank 0 ① → ② → ③ → ④ memtable
rank 1 ① → ② → ③ → ④ memtable
rank N ① → ② → ③ → ④ memtable
训练期间零网络流量 ↓
诊断时 coordinator 按需拉取（南向）
四大收益：
• 训练热路径只做 mmap append，开销可控
• memtable 内存有界，格式统一
• 进程退出后文件仍可 attach 查询
• 路径 A 聚合下推：peer 只返回少量行
有意的 Tradeoff
放弃实时 dashboard 的「好看」，换取训练热路径的「不干扰」。放弃跨 global 表 JOIN 的灵活性，换取联邦查询的正确性和可推理性。这些约束是设计选择，不是技术缺陷。
为什么是创新的
NVIDIA Nsight、PyTorch Profiler、Megatron 内置 profiling 全部走北向汇聚。Probing 是第一个把完整诊断栈嵌入训练进程、数据零上报、查询按需拉取的系统。这个范式选择决定了后续所有设计的走向。

02 技术方案和独特性
创新设计 (二)：五大设计原则及其创新逻辑
每个设计都有明确的 tradeoff，而且这些 tradeoff 是有意为之的
1

SQL 作为统一诊断接口

原则：诊断逻辑写在 skill SQL 中，不在 engine 硬编码分支。
创新理由：传统 profiler 的诊断逻辑硬编码在工具里。Probing 让"找最慢模块"变成一条 SQL，任何诊断逻辑都能被 Agent 自动化执行。engine.rs 只负责注册和路由，新诊断 = 新 skill SQL，不需要改引擎代码。
SELECT module, median(duration)
FROM python.torch_trace
WHERE stage LIKE 'post forward%'
GROUP BY module ORDER BY 2 DESC
2

probe.* 与 global.* 的二象性

原则：同一组物理表的两个视图，差异仅在于是否跨 rank fan-out。
创新理由：coordinator 收到 global.* 时改写为 probe.* 发给 peer。peer 侧永远执行 probe.* — 从根本上杜绝递归联邦。不是两张表，而是同一张表的安全视图切换。
probe.*
本地扫描
单 rank 调试
global.*
联邦 fan-out
跨 rank 聚合
3

六列联邦标签自动注入

原则：合并结果时自动附加 6 列标签，但显式列清单不自动带。
创新理由：这是一个有意的设计约束 — 防止用户在不知情情况下拿到带标签的列导致聚合出错。SELECT * 自动展开标签方便探索；明确指定列时则严格只返回请求的列。安全与灵活的精确平衡。
_host _addr _rank _node_rank _local_rank _role
4

联邦三路径 — SQL AST 级选型

原则：不是字符串匹配，是解析 SQL 抽象语法树判断路由路径。
创新理由：路径 A 检测到可 merge 的 GROUP BY → 各 peer 先聚合，只返回少量行（80% 集群查询走这条路径）。解析失败时保守走 C — 宁可慢，不能错。这是分布式查询优化器在训练诊断场景的首次应用。
路径 A
聚合下推 O(1)
路径 B
联邦扫描 O(N)
路径 C
广播 O(N²)
5

Agent-Native 不是事后添加，是架构第一天就有的

原则：MCP 暴露的 query / run_skill / cluster_query 和 CLI / Web / skill 走的是同一个 Engine::async_query 入口。
创新理由：Agent 不需要学新 API，只需要会写 SQL 或调用 skill。默认只读，写入需 PROBING_MCP_ALLOW_WRITE=1。这不是给传统工具"加个 API"，而是从架构第一天就把 Agent 作为一等公民设计。
{
  "mcpServers": {
    "probing": {
      "url": "http://127.0.0.1:8080/mcp"
    }
  }
}
// 一行配置，Agent 即获得完整的诊断能力

03 技术深度
技术深度 (一)：无锁存储 + 联邦路由
两个设计最精巧的组件，构成了低开销采集和跨节点查询的基础
MEMT 无锁存储格式
环形缓冲区 + generation 计数
固定 chunk 组成环形，回收时 generation+1，读者比较前后值检测并丢弃回收 chunk
单写者 + 无锁读者
写者 &mut self 排他，读者通过 Acquire/Release 内存序完全无锁
三种后端统一抽象
Heap (进程内) / Shm (shm_open 跨进程) / File (mmap 持久化)
per-chunk 字符串去重
DedupState 哈希去重，存储为 4 字节回引用，可节省 20%+ 空间
训练进程写入 mmap 文件，probing 服务器通过同一文件读取 — 零拷贝、零序列化
联邦三路径路由 (~3,066 行)
路径场景传输
A 下推 单表 global.* + SUM/COUNT/MIN/MAX O(1)
B 扫描 单表 global.* 非聚合 O(N)
C 广播 JOIN/CTE/UNION/子查询 O(N²)
基于 sqlparser-rs AST 级分析（非字符串匹配）
查询护栏：强制 broadcast 需 LIMIT，自动注入 LIMIT 10000
每行联邦数据自动附加 6 个标签列：_host, _addr, _rank, _node_rank, _local_rank, _role

03 技术深度
技术深度 (二)：NCCL 等待分解 + Culprit/Victim 归因
整个项目中技术最硬核的部分：从低级时间戳数据到可操作诊断结论的跃迁
Proxy Step Wait 三段分解
SendGpuWait — proxy 等待本地 GPU 完成 send buffer
Culprit 信号：本地 GPU 慢
SendPeerWait (v4) — 等待对端 rank 的 network buffer
接收方拥塞信号
SendWait — 实际发送操作耗时
首次进入优先设计：只有第一次进入某状态时才记录起始时间戳，正确处理 proxy progress loop 重试行为。

引用计数完成模型：通过 live_children + stopped 标志判断 collective 是否真正完成，处理异步完成语义。
Culprit/Victim 自动归因
Culprit（罪魁）
send 边 (rank→peer) 上的高 send_gpu_wait_ns
本地 GPU 慢，导致其他 rank 等待
Victim（受害者）
recv 边上的高 recv_wait_ns
等待对端发送，自身无过错
Propagated Victim

总结：Probing 的核心价值

价值与意义

Probing 之于 AI 训练诊断 ≈ K8s 之于容器编排。从碎片化工具（Nsight/PyTorch Profiler/Megatron）到统一 SQL + Agent 接口。但约束更硬：K8s 管无状态容器可重启，Probing 管有状态训练进程不能中断、不能有可感知开销——这是更深的护城河。

技术独特性

四层架构 + 6 契约 + 没有北向流量 + SQL 统一接口 + probe.*/global.* 二象性 + 联邦三路径 AST 路由 + 无锁 mmap 存储 + 分布式火焰图 + Python 变量跟踪 + 分布式热力图 + NCCL 等待分解 + 声明式 Skill + MCP 接口。6 项业界首创构成护城河。

技术领先性

10 款工具逐维度对比，加权总分 3.85 领先但差距不大。架构与分布式诊断是核心优势，易用性 (3.0) 和生态成熟度 (2.5) 是最大短板。差异化能力 5 项，但尚未转化为采用优势。

增长前景

目标用户：AI Infra / 平台团队（百卡以上集群）。框架无关统一接入（PROBING=1 通吃 Megatron/DeepSpeed/FSDP），AI Agent 自动诊断闭环（<1 分钟出结论）。增长飞轮：Infra 部署 → 业务方零改动接入 → Agent 自动诊断 → Skill 沉淀经验 → 更多场景。路径和 K8s 一致：诊断工具 → 诊断平台 → 训练可观测性标准（Skill 生态 + MCP 接口）。
